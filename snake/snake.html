Snake

SystemVerilog on a UPDuino to implement the Snake Arcade Game.

Field: EE

Specific: Digital Logic

Duration: Nov. 2025 - Jan. 2025

Skills: SystemVerilog, Python, FPGA, breadboard prototyping, Git

Overview

A completely hardware-based implementation of the classic Snake game using SystemVerilog on an FPGA, featuring VGA video output and an NES controller for user input. The game runs on a 480×640 VGA display using 20×20 macropixels, resulting in a discrete 23×22 grid where the snake moves at a slowed game clock for a retro visual effect. Game logic is managed via a finite state machine that handles movement, eating apples, scoring, growth, collision detection, and game-over behavior. Apples spawn at pseudo-random locations using LFSR-based random number generation, while graphics such as the snake, apple, score digits, and game-over screen are rendered using ROM-based pixel art and real-time VGA coordinate calculations. The system integrates multiple clock domains, NES input decoding, visual and audio feedback, and modular design to produce a fully playable and stable Snake game running entirely on hardware.

Challenges & Solutions

Challenge: Debugging the NES

When testing our NES controller, we found that pressing up didn't always result in upward motion, and the same issue occured with every other direction. Sometimes pressing up would result in leftward motion (or quite literally any other direction). Diagnosing the cause of this bug proved to be difficult, as our typical strategies of print statements would be extremely difficult on an FPGA.

*Swipe for problem diagnosis.*

Diagnosis: Perpetually high latch

We partially diagnosed the problem by altering our display to a testing version, where upwards motion would result in the entire screen becoming teal, rightward motion green; each direction had a color. When pressing any single button, the screen would appear with stripes of different colors, indicating somehow there were conflicting signals simultaneously or rapidly alternating.

What should happen: latch goes high -> right burron is pressed -> controller's internal circuits transmit signal to FPGA -> latch pulse goes low -> controller outputs 8 bits serially -> 8 clock pulses result in 8 bits read to be decoded.

What actually happens: Our internal latch signal was perpetually high, this was the signal that supposedly triggered a "moment" to capture signals in the NES controller. With the latch always high, the current state was captured and recaptured forever, never outputting serial data. Thus, the shift register outputs we were using for our game logic must have contain garbage values. The "serial" data was not being read in as intended, thus was likely floating, or at previous values, which then read as random, and were shifted into our shift register, providing illogical values indicating multiple directions being pressed at once.

*Swipe for Problem Solution.*

Solution:

Steps to correct readings from NES (1) Latch HIGH (2) Latch LOW (3) 8 clock edges. Our code was missing step two. After adding this step, the NES began reading the button presses correctly.

Challenge: Memory Constraints

All memory is limited. We decided to implement graphics stored in ROM instances for many of our more detailed visuals, including the apple, numbers, letters, and game over screen. As such, limited remaining look up tables remained for other purposes.

This became an issue primarily when we began implementing the snake's incrementing length as it consumes apples. Our best method to handle the dynamic nature of the snakes length was to use a large register to hold the x & y coordinates of each segment, and an additional register to hold the length of the snake to signify which coordinates were significant. The size of this register became limited by our FPGA memory.
